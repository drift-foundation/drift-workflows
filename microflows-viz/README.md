# microflows-viz — live workflow lifecycle visualizer

> Standalone tool (not part of the `microflows` drift build). Starts as the higher-ups demo player; designed to grow into a path/trace visualizer + diagnostic tool over the coordinator's durable state.

An **animated state-machine** view of a Microflows workflow, for the higher-ups demo. The diagram is a
faithful model of the durable coordinator (the seven workflow states in `state.drift`), and it's driven
by the **real audit-event kinds** the coordinator appends to `tb_mf_workflow_event`. Four scenarios:

1. **Happy path** — `reserve → charge → completed`.
2. **Reject → compensation** — `charge` fails; `reserve` is auto-unwound (the saga model).
3. **Persistent route-404 → blocked ★** — a participant goes dark; the durable reconcile budget bounds
   the retries, then parks the workflow for an operator (the new #2 safety behavior).
4. **Result branch + authored fail** — `case result … { fail "payment_declined" }` → unwind.
5. **Compensation fails → blocked (reverse) ★** — the ops worst case: a settled side-effect can't be
   undone (the participant rejects the `release`), so the workflow parks for an operator with the
   reservation stranded — `blocked_resolution`, checkpoint `resolution_required`.

## Run it (the demo player)

`index.html` is **fully self-contained** — no CDN, no second tab, no network. The diagram renders and
highlights **right on the page**, and **Play replays cleanly every time**.

```bash
# either just double-click index.html, or serve it:
cd microflows-viz && python3 -m http.server 8080   # open http://localhost:8080
```

Pick a scenario (top-right) → **▶ Play**. Three synced views (toggle top-left):

- **Sequence** (default) — the actual **calls**, one step per event: `uflowsd → participant: PUT reserve`,
  `← 200 reserved`, `→ MariaDB: settle + checkpoint`, the route-404 retries, the compensation PUTs, etc.
- **IR graph** — the compiled **plan** as a flowchart (operation nodes, `case` branches, `fail`, `return`),
  with the **live node highlighting** as the workflow advances (blue = active, red = fail, purple = blocked,
  orange = compensating, green = done). The flowcharts are **real lowered IR** — generated by
  `mfrunner --emit-graph` (see below) — and rendered by the **embedded Mermaid**.
- **State machine** — the durable lifecycle (`state.drift` states 1–7); best for the failure /
  compensation / blocked story where the state genuinely moves.
- **MF plan** — the **actual `.mf` language source** behind the current scenario (from `plans/`; several
  scenarios share one plan — the difference is what happens at runtime).

Click any **Trace** line to expand the **in/out payload** for that step (the PUT input, the `200` result,
the compensation **forward envelope** `{forward:{input,result}}`, the durable blocked continuation, …).
These payloads are illustrative in the demo; against a real run they'd be `tb_mf_workflow_event.payload`.

All three animate in lockstep with the *Trace* panel (the append-only event log). **⟲ Reset** or switching
scenarios re-arms it; the status strip shows the durable sub-phase (`driving · awaiting · reconciling`),
current op, reconcile-attempt count, and block reason.

> **Embedded, no network.** `vendor/mermaid.min.js` (~3.5 MB, Mermaid 11.16.0) is vendored in-repo so the
> IR view renders in a fully isolated environment — the page makes **zero outside calls**.

### IR graphs are generated from real `.mf` (`--emit-graph`)

The runner has a DB-free flag that lowers a `.mf` to its IR and prints a Mermaid `flowchart`:

```bash
mfrunner --emit-graph plans/reserve_charge.mf
#  flowchart TD
#    n0["reserve"] --> n1
#    n1["charge"]  --> n2
#    n2(["return"]):::term
```

The four IR graphs embedded in `index.html` were generated this way from `plans/*.mf`
(`reserve_charge`, `reserve_only`, `authorize_decline`) — node ids (`n0`, `n1`, …) are the runner's own.
To refresh or add one: edit/add a `plans/*.mf`, run `--emit-graph`, and paste the output into the `IR`
map in `index.html` (the highlight steps reference the `n`-ids). The flag works on any real workflow too,
e.g. `--emit-graph ../microflows/examples/workflows/checkout_branch_merge.mf` (branch + merge).

## Alternative views (optional, hosted)

The `microflows.machine.js` XState model powers two hosted views if you want auto-layout / interactivity:

- **Stately editor** — open <https://stately.ai/editor>, *Create → Import → code*, paste
  `microflows.machine.js` (change the first import to `from 'xstate'`). Auto-laid-out diagram with each
  state's description + a **Simulate** mode you click through. (Hosted; needs network.)
- **Your own XState app:** `import { microflowsMachine } from './microflows.machine.js'`.

> The self-contained `index.html` above is the recommended path for a live demo — the hosted Stately
> *inspector* renders only the first actor and won't refresh on replay, which is why the player no longer
> depends on it.

## Drive it from a REAL run (optional, highest credibility)

The tapes in `scenarios.js` mirror real `coordinator-singular` integration runs. To replay an **actual**
workflow instead, point `export_events.py` at a live coordinator DB:

```bash
python3 export_events.py --workflow-id <hex32> --database microflows
```

It prints the real event timeline and a `scenarios.js`-ready tape (mapping each durable `kind` to a
machine event). Drop that in `scenarios.js` and Play.

## Presenter cheat-sheet — the ★ route-404 story (the strongest "why this matters")

> "A participant — a payment gateway, say — disappears behind a bad load-balancer. Watch: the
> coordinator confirms there's genuinely no record (`participant_route_404`), and instead of failing
> the payment (which could be a transient blip) or retrying forever, it spends a **durable, bounded
> budget** — count + wall-time, and a *resume can't reset it*. When the budget is spent, the workflow
> doesn't fail and doesn't silently hang — it moves to **`blocked`** and waits for an operator, with
> the reason recorded durably. Every state you see is a fenced, atomic commit in the database; if the
> runner crashed mid-flight, recovery replays to the exact same picture."
