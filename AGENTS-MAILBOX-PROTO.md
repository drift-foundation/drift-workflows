# Agent Mailbox Protocol

Protocol version: **5**
Status: **active local trial in `drift-lang`**

## Purpose and scope

Baton is the repository-wide notification and exclusive-claim protocol for coordination under `work/`. Every ready handoff, active claim, and live broadcast is a direct child of the ignored transport directory `work/mailbox/`, so consumers never recursively scan findings and Git never sees live protocol state. Durable handoffs point to retained details in a top-level or nested `work/finding-*` folder or another regular subdirectory beneath `work/`; transient handoffs embed their content in the mailbox envelope.

Protocol v5 provides:

- arbitrary repository-configured roles rather than hard-coded reviewer/implementer routing;
- explicit sender and recipient roles in every directed filename;
- atomic single-winner claims for directed work;
- immutable, non-claimable broadcasts with recipient-local seen receipts;
- author-owned expiration cleanup for broadcasts;
- immutable JSON envelopes whose routing fields are checked against their filenames;
- explicit `durable` and `transient` retention, so audit material is retained while short-lived coordination content cleans itself up;
- stream semantics: every publication is an independent message, and a thread may contain any number of updates, results, corrections, and final responses.

Use `tools/baton/baton` for all mailbox discovery, publication, claims, responses, notice observation, and cleanup. Do not manually recreate those transitions.

## Roles and identities

Roles are data declared in `tools/baton/roles.json`. Baton contains no role-specific routing table. Adding a planner, designer, security reviewer, linter, or other participant means adding its role configuration, not adding role-specific actions.

A role slug uses lowercase ASCII letters, digits, and underscores, begins with a letter, and contains no hyphen: `[a-z][a-z0-9_]*`. `all` is reserved as the broadcast selector and cannot be configured as a role.

Each configured role chooses one identity mode:

- `agent`: the invocation supplies a stable actor slug and a per-live-instance seed of at least 128 random bits as lowercase hexadecimal;
- `singleton`: the configuration names its one actor, and invocations supply neither `--actor` nor `--seed`.

Actor slugs use lowercase letters, digits, hyphens, or underscores. The actor answers **who** acted; the seed distinguishes concurrent live instances of the same actor. Seeds are coordination identities, not security credentials.

## Directed message names

An unclaimed directed handoff is a direct child of `work/mailbox/`:

```text
PENDING-FROM-<sender-role>-TO-<recipient-role>-<UTC-timestamp>-<message-id>
```

An active claim is the exact pending file atomically renamed in place:

```text
CLAIMED-FROM-<sender-role>-TO-<recipient-role>-<UTC-timestamp>-<message-id>-BY-<actor>-SEED-<seed>-AT-<UTC-timestamp>
```

Singleton claimants omit the `-SEED-<seed>` component. Separators are single hyphens; v5 does not use doubled `--` separators. Timestamps use `YYYY-MM-DDTHH-MM-SSZ`, and message IDs are collision-resistant lowercase hexadecimal values generated by Baton.

Only the role named by `TO` may claim a directed handoff. The filename alone exposes routing and ownership; the envelope independently repeats and validates them.

## Broadcast notice names

A broadcast is a direct child of `work/mailbox/`:

```text
NOTICE-FROM-<sender-role>-TO-ALL-<UTC-timestamp>-<message-id>
```

`ALL` is a reserved audience marker, not a role. A broadcast notice:

- is immutable and cannot be claimed or renamed to `CLAIMED-*`;
- is visible to every configured role and agent instance except the exact author instance;
- carries a required `expires_at` value in its envelope;
- is observed independently by each recipient through an immutable local seen receipt;
- does not establish exclusive work ownership;
- may be removed after expiration only by the exact original author instance through `baton expire`.

A response requested by a broadcast is a new ordinary directed message; the broadcast itself is never converted into work. If the author identity or its publication receipt is lost, the expired notice remains until Slawomir explicitly authorizes recovery.

## Immutable envelope and retention

Every v5 mailbox file contains one newline-terminated JSON object. Every directed handoff contains exactly these common fields:

- `protocol_version`: `5`;
- `message_type`: `handoff`;
- `message_id`;
- `from_role` and `to_role`;
- `created_at`;
- `retention`: `durable` or `transient`;
- `kind`: a caller-selected semantic label;
- `thread_id`: stable when messages belong to the same conversation;
- `outcome`: a caller-selected result label or `null`;
- `responds_to`: the exact incoming `CLAIMED-*` basename for a reply, otherwise `null`;
- `author_actor` and `author_seed`.

A `durable` envelope additionally contains exactly one `target`: a normalized path relative to `work/`. A `transient` envelope instead contains exactly one `body`: non-empty UTF-8 text of at most 64 KiB. A message never contains both `target` and `body`.

Broadcasts use `message_type: notice`, `to_role: ALL`, and add the required `expires_at` timestamp. Singleton authors encode `author_seed` as `null`.

The envelope routing, timestamp, and message ID must match the filename. A durable target must already exist as a regular non-symlink file beneath the real `work/` directory and must not be inside `work/mailbox/`. Absolute paths, traversal components, symlink escapes, missing targets, extra or missing envelope fields, unknown roles, malformed timestamps, invalid retention combinations, and oversized or invalid transient bodies are protocol errors. Durable publication requires a real subdirectory beneath `work/`; generic coordination uses transient retention instead of leaving loose detail files at the `work/` root.

## Content authorities

- Use `durable` for reviews, implementation reports, approvals, evidence, decisions, or anything that must survive message consumption. The mailbox envelope is an immutable pointer; its target is the substantive retained authority.
- `review-YYYY-MM-DDTHH-MM-SSZ.md` remains immutable reviewer input when the repository finding workflow requires that convention.
- `PROGRESS.md` remains implementer-owned. If a durable handoff points directly to it, its contents are frozen for the lifetime of that pending or claimed snapshot.
- Use `transient` for short-lived coordination whose body should disappear with the message, such as readiness signals, acknowledgements, and tooling announcements. Its JSON envelope is both notification and content authority.
- Consuming a directed durable message removes its envelope but retains its detail. Consuming a transient message removes the envelope and therefore its body.
- Expiring a durable broadcast retains its target detail. Expiring a transient broadcast removes its envelope and embedded body.

## Atomic publication and immutability

For a durable message, Baton publishes the detail first and its `work/mailbox/` envelope second. For a transient message, the complete body is part of the one envelope publication. Every published file is written completely under a unique hidden temporary name in the same directory, flushed, validated, and atomically renamed into its absent final name with `renameat2(RENAME_NOREPLACE)`. A race never replaces an existing path.

After publication:

- nobody edits, truncates, retargets, replaces, or recreates the mailbox file, embedded body, or frozen target;
- corrections and addenda use a new `send` with a new message ID; durable corrections also use a new detail;
- only a directed recipient may perform its atomic `PENDING -> CLAIMED` rename;
- only that exact claimant instance may publish the response and pop its claim;
- only a broadcast's exact author instance may remove it, and only after its recorded expiry and hash checks pass.

The final rule is the sole ordinary sender-removal exception. Directed senders never withdraw or pop their own messages.

## Directed PUSH -> CLAIM -> PUSH -> POP lifecycle

Every directed handoff follows this state machine:

1. **PUSH content:** for durable retention, the sender atomically publishes the complete immutable detail; for transient retention, the body is prepared for the envelope.
2. **PUSH pending:** the sender atomically publishes the matching `PENDING-FROM-X-TO-Y-*` envelope.
3. **CLAIM:** one instance of role `Y` wins the same-filesystem no-clobber rename.
4. **WORK immediately:** only that claimant processes the frozen snapshot. Claim only when ready to start; if occupied with another task, leave the handoff pending for later. A claimed-but-unworked handoff blocks every other eligible consumer and is a workflow deadlock even though the claim has no timeout.
5. **PUSH response:** `reply` atomically publishes the outgoing content and directed envelope before consuming the incoming claim. The recipient defaults to the incoming sender but may be explicitly forwarded with `--to`. A response inherits the incoming retention unless `--retention` explicitly selects the other policy. `close` deliberately creates no outgoing envelope; a durable close retains its terminal detail, while a transient close retains nothing.
6. **POP claim:** only the exact claimant removes its claim and claim receipt after the response or close transition is safe.

Claims have no timeout. Long reviews, research, compilation, and test runs are normal. Elapsed time never authorizes stealing, deleting, or requeueing another instance's claim.

## Broadcast lifecycle

1. The author uses `send all`; Baton publishes the selected durable or transient content and `NOTICE-FROM-X-TO-ALL-*` envelope, then records an author receipt containing notice and authoritative-content hashes.
2. `scan` reports unexpired notices not yet seen by the invoking identity.
3. `wait` records a seen receipt and returns the notice when no directed handoff was claimed. `see` performs that operation for an exact notice basename. Neither action mutates the notice.
4. At `expires_at`, the notice stops being delivered as unseen.
5. The author invokes `expire` with the exact notice basename. Baton validates role, actor, seed, expiry, author receipt, notice hash, retention, and authoritative-content hash before removing the notice and author receipt. A durable target remains; a transient body disappears with its envelope.

Recipient seen receipts and author receipts live outside the repository under Baton's per-repository `/tmp` receipt directory. Losing the author receipt fails closed and requires explicit human recovery; Baton does not infer or steal authorship from filename text alone.

## Message streams

A thread is a correlation label, not a lock and not a one-request/one-response limit. Any role may publish any number of independent messages in a thread. For example, an implementer may send an interim status while tests run and later send a separate results message; a reviewer may likewise send an addendum or correction as a new message.

Every exact `PENDING-*`/`CLAIMED-*` envelope still has one consumer and one terminal transition: its claimant invokes `reply` or `close` once, and that exact claim is popped. Additional updates are new `send` operations with new message IDs, normally reusing `--thread`. They may be published before or after another message in the thread is consumed. Never edit or republish an existing envelope to simulate an update.

## Generic action surface

All roles use the same actions:

- `send TO_ROLE DESTINATION [BODY_FILE|-]`: publish a durable directed handoff by default; `DESTINATION` must name a real subdirectory beneath `work/`, and `TO_ROLE=all` publishes a durable broadcast notice;
- `send TO_ROLE [BODY_FILE|-] --retention transient`: publish an envelope-embedded transient handoff or broadcast, with no destination argument;
- `scan`: report directed work, unseen notices, expired notices owned by the caller, and active claims;
- `claim [PENDING]`: atomically claim the named handoff, or the next handoff addressed to the role when omitted;
- `wait`: use `inotify`, with a defensive 60-second rescan by default, until it claims one directed handoff or records one unseen notice;
- `see NOTICE`: record and return one broadcast without claiming it;
- `reply CLAIM [BODY_FILE|-]`: publish the response first, then pop the incoming claim;
- `close CLAIM [BODY_FILE|-]`: publish a terminal detail without an outgoing message, then pop the claim;
- `expire NOTICE`: author-clean one expired broadcast;
- `doctor`: validate recognized mailbox state.

`--kind`, `--thread`, and `--outcome` carry workflow meaning without introducing role-specific verbs. Human approval is therefore a normal reply such as `human reply ... --outcome approved`, not a hard-coded `approve` action. `send` defaults to `--retention durable`; `reply` and `close` inherit the incoming message's retention unless explicitly overridden. Switching a transient incoming message to a durable response requires `--destination`, because there is no incoming target directory to inherit.

Except for `wait`, every action performs one bounded transition and exits. Do not pass `--interval 60`; 60 seconds is already the default. Specify `--interval` only when deliberately choosing another defensive rescan interval.

`wait` is a consumer and claim operation, not a passive notification watcher. One actor/seed instance must run exactly one consumer path at a time: either one `wait`, one argument-less `claim`, or one explicit `claim PENDING`. Never leave `wait` active while issuing a manual claim, and never run two waits with the same actor/seed. Arm `wait` only when the actor is prepared to interrupt other non-claimed work and immediately process whatever it claims; otherwise postpone consumption and leave the message pending. An armed subprocess is not sufficient monitoring when the agent interface does not wake automatically: the responsible agent must keep its turn active and continuously harvest the wait result, rather than finalize and rely on a later user prompt. When `wait` returns `status: claimed`, that returned claim is the instance's active work: begin processing it immediately and `reply`/`close` before starting another consumer. If duplicate invocations race, the single winning claim remains valid and the loser fails with the existing-claim guard; do not claim again or repair the mailbox.

## Failure and recovery

Malformed messages, missing receipts, hash drift, ownership mismatches, and lost atomic races fail closed. Do not edit, remove, recreate, or manually requeue the affected path. Preserve exact state and ask Slawomir for a recovery ruling naming the specific message and action.

Protocol-v3 `REVIEW-PENDING`, `IMPL-PENDING`, `APPROVAL-PENDING`, and doubled-separator `CLAIMED--*` files are not valid v5 work and cannot be consumed by Baton. Protocol-v4 envelopes are likewise not valid v5 messages. `doctor` also reports any transport token stranded at the old flat `work/` level. Recognized incompatible or misplaced state requires explicit human recovery. V5 provides no legacy publication mode, compatibility alias, or dual reader.

## Terminal reviews and finding lifecycle

- A review requesting more work uses `reply` before its implementation claim is popped.
- A signing-off review uses `close`; it creates no pending response and therefore cannot deadlock in a final-review loop. Use durable retention when the signoff itself must remain in the finding journal.
- On terminal signoff, the reviewer ends the user-facing handoff with exactly `finished`.
- Never delete, archive, or relocate a finding while any directed message, claim, or unexpired notice points into it.
- Finding details remain subject to the ownership, nesting, review-journal, and cleanup rules in `AGENTS.md`.

## Trial and distribution

Version 5 adds explicit durable/transient retention, formal message-stream semantics, and an ignored `work/mailbox/` transport root to the configured-role, full-`FROM/TO` protocol. Its local trial is active in `drift-lang`. Peer repositories remain on their presently distributed protocol until Slawomir explicitly approves v5 distribution.
